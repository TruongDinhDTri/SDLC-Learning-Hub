## Purpose

Deployment is where theory meets production reality. Enterprise deployment is about minimizing risk — not just shipping code as fast as possible.

## Gradual Rollout Strategy

Release progressively to reduce the blast radius of any issues:

1. **Internal users only** — team members test in production
2. **Beta users** — opted-in early adopters, 1-5% of users
3. **Small traffic slice** — 5-10% of all traffic
4. **Geographic rollout** — one region or market first
5. **Full release** — 100% of users

At each stage: observe metrics → decide to proceed or rollback.

## Monitor in Real-Time During Release

| Metric | Alert Threshold |
|--------|----------------|
| Error rate | Above 1% (baseline: 0.1%) |
| Latency p95 | Above 500ms (baseline: 150ms) |
| DB connection errors | Any spike above baseline |
| Queue depth | Above 2x normal |
| Memory usage | Above 90% |

Have monitoring dashboards open during every significant deployment.

## Rollback Planning

Ask this question BEFORE every deployment:

```
How do we undo this safely if something goes wrong?
- Is the DB migration reversible?
- Can we disable the feature via feature flag?
- Is there a tested and documented rollback procedure?
- What data loss risk exists if we rollback mid-flight?
```

Deployments without rollback plans are reckless. This is a real senior engineering question.

<Callout type="warn" title="Never Deploy on Fridays">
Enterprise rule: avoid deploying on Fridays or before holidays. If something breaks, you want engineers available and focused to fix it. Friday deploys are for teams that enjoy weekend incidents.
</Callout>
